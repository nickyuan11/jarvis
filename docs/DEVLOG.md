# Jarvis 开发日志

一个基于 Spring Boot 4 和 Spring AI 的个人 AI 助手（AI Agent）。目标是像钢铁侠里的 Jarvis 一样，在生活和工作中都能帮上忙：
- **能做事**：通过工具调用管理提醒事项、查询关注的比赛结果
- **懂你的资料**：个人知识库（RAG），回答时注明出处
- **记得你**：跨会话的长期记忆
- **会主动**：每日简报、到点提醒

## 2026-10-26（周一）：环境搭建 + 第一次和 Jarvis 对话

**成果**
- 搭好开发环境：JDK 21、MySQL 8、IDEA、Git。
- 创建 Spring Boot 4 项目，完成第一个接口 `GET /api/ping`。
- 设计并建好三张表：`user`、`conversation`、`message`，接入 MyBatis-Plus（自动填充时间、逻辑删除）。
- 接入 DeepSeek，完成 `POST /api/chat`：支持多轮对话记忆，记录每次回复的模型和 token 用量。
- 代码第一次推送到 GitHub。

**设计讨论：message 表**
- 主键用 `bigint`；去掉冗余的 `userId`，通过会话关联用户。
- `role` 用字符串 `user / assistant / system / tool`，和大模型 API 格式一致，可以直接转换，也方便以后扩展工具调用。
- token 拆成 `prompt_tokens` 和 `completion_tokens`，并记录 `model`：输入和输出单价不同、价格随模型变化，存原始数据，费用可以随时算。
- 时间用 `LocalDateTime`，不用旧的 `java.util.Date`。

**踩过的坑**
- **Maven 下载依赖失败**：报错 `Permission denied: getsockopt`。原因是 ExpressVPN 拦截了 Java 程序的网络连接。解决：调整 VPN 设置，并在 `settings.xml` 配置阿里云镜像。
- **调用 DeepSeek 失败**：同样的报错，这次是项目运行用的 JDK 21 被拦截（IDEA 下载依赖用的是它自带的 Java，所以之前没暴露）。解决方法同上。
- **测试时出现 Mockito 动态加载 agent 的警告**：JDK 21 对动态加载 agent 发出的提醒，不影响运行，暂不处理。

**学到的**
- 测试类上的 `@Transactional` 会在每个测试结束后自动回滚，测试数据不会留在库里；但自增 id 不会回退。
- 调用大模型不要放在数据库事务里：响应要好几秒，会长时间占用数据库连接。
- 大模型本身没有记忆，“记住对话”其实是每次把历史消息一起发过去。

## 2026-10-27（周二）：流式输出、会话管理、登录

**成果**
- **流式输出**：新增 `POST /api/chat/stream`，通过 SSE 一段段推送回复；定义了 `meta / delta / done / error` 四种事件。
- **聊天网页**：`index.html`，回复逐段显示，展示模型和 token 用量。
- **会话管理**：左侧会话栏，支持查看历史、继续聊天、重命名、删除。
- **注册登录**：Spring Security + JWT，密码 BCrypt 加密，新增登录注册页；所有数据按登录用户隔离。

**设计要点**
- 流式回复在整个流结束后才一次性存库；用户中途关闭页面时，保存已生成的部分；模型出错时推送 `error` 事件，而不是直接断开连接。
- 数据库操作通过 `publishOn(Schedulers.boundedElastic())` 切到专门的线程池，避免阻塞负责网络 I/O 的线程。
- 前端用 `textContent` 显示 AI 回复，防止 XSS。
- 接口按 RESTful 风格设计（GET 查询、PATCH 部分修改、DELETE 删除，成功返回 204）。
- 每个会话操作都校验归属，防止越权访问（IDOR）；“不存在”和“不属于你”统一返回 404。
- 把“当前用户”集中在 `CurrentUser` 一个地方。接入登录时只改了它，业务代码一行没动。
- 登录失败统一提示“用户名或密码错误”；注册并发时由数据库唯一索引兜底。

**踩过的坑**
- **注册接口返回 400 但没有错误原因**：Spring Boot 4 把 `server.error.include-message` 改名为 `spring.web.error.include-message`，旧配置不报错但不生效。教训：升级大版本后，配置不生效要先查迁移说明。
- **用户名带空格导致注册失败，但提示不清楚**：优化为注册时实时提示规则、提交前前端校验、后端报错写明“不能包含空格、中文”。前端校验只为体验，后端校验才是防线。
- **新文件漏提交**：IDEA 默认不勾选新文件，用 Amend 合并进上一次未推送的提交。
- **推送 GitHub 失败**：ExpressVPN 分流没有包含 Git。把 `git-remote-https.exe` 等加入分流后，网络稳定时推送成功。

**面试题思考：JWT 如何让用户下线**
- 单个 JWT 签发后无法收回，被偷后在过期前都能用。
- 方案：双 token（短期 Access + 服务端登记的 Refresh）、token 黑名单、用户版本号。
- 三种方案都需要在服务端存少量状态，通常放在 Redis（快、支持自动过期）。

## 2026-11-01（周日）：Docker + Redis

**成果**
- 装好 WSL2 和 Docker Desktop，用 `compose.yaml` 启动 Redis。
- **真正的退出登录**：新增 `POST /api/auth/logout`。每个 JWT 带唯一编号 `jti`，退出时写入 Redis 黑名单，过期时间等于 token 剩余寿命。用旧 token 访问接口返回 401。
- **聊天接口限流**：每个用户 60 秒内最多 10 条消息，超出返回 429，前端显示需要等待的秒数。

**设计要点**
- 限流用 Lua 脚本把 `INCR` 和 `EXPIRE` 合成一个原子操作，避免计数器永不过期、用户被永久限流。
- 先限流再干活：被拒绝的请求不写数据库，也不调用大模型，不产生费用。
- 固定窗口限流的缺点：窗口交界处可能在短时间内放过两倍请求。改进方向是滑动窗口或令牌桶。
- Redis 故障时选择“失败关闭”：黑名单和限流关系到安全和费用，宁可请求失败也不跳过检查；纯体验类功能（如缓存）才适合降级跳过。

**踩过的坑**
- **WSL 安装失败**：`wsl --install` 默认会下载 Ubuntu，体积大、容易失败。Docker 只需要 WSL 本身，改用 `wsl --install --no-distribution --web-download`。
- **Docker 新版安装程序不能选目录**：默认装在 `C:\Program Files\Docker\Docker`；镜像数据目录可以在设置里改到 D 盘。
- **拉取镜像报 `EOF`**：连不上 Docker Hub。镜像下载发生在 WSL 虚拟机里，VPN 按应用分流抓不到这部分流量。临时让所有流量走 VPN，拉完镜像再改回分流。
- **PowerShell 看不到 401**：`Invoke-RestMethod` 只把错误响应的内容显示成报错，用 `curl.exe -i` 才能看到状态码。

**单元测试**
- 新增 5 个纯单元测试类（JUnit 5 + Mockito + AssertJ），不依赖数据库和 Redis，几秒内跑完。
- 覆盖：JWT 篡改/过期/错误密钥被拒绝、密码以哈希存储、并发注册撞唯一索引、登录失败提示一致、退出后 token 进黑名单、限流边界、越权访问返回 404。
- 原则：数据库和 Redis 等外部依赖用 Mock；BCrypt、JWT 这类本身就是被测逻辑的用真实实现。

**方向调整：从“网文 RAG”升级为个人 AI Agent**
- 原因：演示网文涉及版权；更想让 Jarvis 在生活和工作中都有用，也能给其他用户使用。
- RAG 技术点保留，改为“个人知识库”：用户上传自己的资料，没有版权问题。
- 原则：每种能力先做一个最实用的场景，做深做稳，避免功能铺太开、每个都很浅。
- 新计划：
  1. 第 3 周：工具调用，先做“提醒事项”和“比赛结果”
  2. 第 4 周：个人知识库（RAG + pgvector）+ 长期记忆
  3. 第 5 周：每日简报、语音交互、部署上线

**工具调用（Agent）：提醒事项 + NBA 比赛**
- 新增 `reminder`、`notification` 两张表；提醒支持不重复/每天/每周/每月。
- 3 个提醒工具（创建、查看、取消）和 3 个 NBA 工具（最近比赛、接下来的比赛、球员数据），用 Spring AI 的 `@Tool` 注册给大模型。
- 定时任务每 30 秒扫描到期提醒，写入站内通知；前端每 30 秒轮询，右上角弹框，页面在后台时发浏览器系统通知。
- NBA 数据来自 ESPN 公开接口，整理成简短文本再交给模型，结果缓存在 Redis。

**Agent 原理**
- 大模型自己不执行代码，只决定“调用哪个工具、传什么参数”，真正执行的是 Java 程序；“思考 → 调用工具 → 看结果 → 再思考”的循环就是 Agent 的本质。
- `@Tool` 的描述就是给模型看的接口文档，模型完全靠它判断何时调用。
- 一次多轮工具调用的问答用了 1.3 万输入 token：每轮都要把对话、工具说明和结果重新发一遍，这是 Agent 应用的真实成本。

**设计要点**
- 每次请求在系统提示词里带上当前时间和星期，模型才能把“明天下午 3 点”换算成具体时间。
- 用户 id 通过 `ToolContext` 在服务端传给工具，模型看不到也改不了；流式对话时工具可能在别的线程执行，也拿不到 `SecurityContext`。
- 工具出错时返回说明而不是抛异常，模型能据此向用户解释或修正参数重试。
- 循环提醒采用“下一次提醒时间”模式：触发后把 `remind_at` 推到下一个未来的周期，停机后不会补发多次。
- 用带原状态和原时间的条件更新（乐观锁）抢占提醒，多实例部署也不会重复发送。
- NBA 缓存失败时直接查源数据（缓存只是加速）；而黑名单、限流选择失败关闭（关系到安全和费用）。

**踩过的坑**
- **启动报 `No default constructor found`**：`JarvisTime` 有两个构造器，Spring 不知道用哪个。多构造器时要用 `@Autowired` 标明；单构造器的类不需要。读 Spring 启动报错要看最里层的 `Error creating bean`。
- **IDEA 把我写入的文件又覆盖回旧版本**：文件在 IDEA 里开着时，IDEA 会把内存里的旧内容存回磁盘。约定：改文件前先关掉对应标签页，写完再核对文件大小。
- **Fandom（LoL 数据）被限流**：通过 VPN 访问时和大量用户共用出口 IP，一两次请求就触发限流，作为数据源不可靠。LoL 改为调研 PandaScore。
- **ESPN 返回 403**：Java 默认的 User-Agent 被 Akamai 防护拦截。改为如实声明 `Jarvis/0.1`，没有伪装成浏览器。部署到云服务器后可能仍会被拦，上线前需换成正规的带 Key 的数据源。
- **模型用过时的记忆反驳用户**：它记得詹姆斯在湖人，不相信用户说的 76 人。在提示词里明确“用户提供的近况和工具结果比模型记忆更可信”；工具也改为列出未出场球员，让模型分清“没上场”和“不在这支球队”。
- **模型“自我否认”提醒时间**：查看提醒的工具只返回待提醒事项，模型又不知道历史消息的发送时间，于是编出“我之前时间算错了、提醒没设成功”的解释（幻觉）。改为同时返回最近 24 小时已提醒/已取消的事项，并给历史中的用户消息加上发送时间。
- **修改数据处理逻辑后要清旧缓存**：否则还会读到旧格式的结果。更好的做法是在缓存 key 里带版本号。

**思考题：用户没打开网页，提醒怎么送达？**
- 轮询只在页面打开时有效。改进方向是多渠道推送：保存用户的邮箱或手机号，到点时同时发站内通知和邮件/短信。

## 2026-11-02（周一）：英雄联盟赛事工具

**成果**
- 接入 PandaScore（免费套餐包含 LoL 赛程和比赛结果），新增两个工具：某支战队最近的比赛、正在进行和即将开始的比赛（不指定战队时返回世界赛赛程）。
- 用户说“B站那个队”，模型能自己换算成 BLG；查完 T1 的赛程后，还会主动问“要设个提醒吗”，把查赛程和设提醒两种工具联系起来。

**设计要点**
- PandaScore 的 token 放在请求头里，不拼在 URL 上：URL 容易出现在访问日志、监控和报错信息里。
- 按名字搜索是模糊匹配，返回后再核对参赛队伍里确实有这个简称。
- 没配置 token 时只有 LoL 工具不可用，不影响启动；而 JWT 密钥缺失会直接启动失败。配置项越关键，缺失时处理越严格。
- NBA 和 LoL 都需要“先查缓存、没有再请求”的逻辑，抽成公共的 `TextCache`；NBA 缓存 key 加上版本号 `v2`。

**踩过的坑**
- **PowerShell 测 PandaScore 返回空白**：以为是免费套餐不含 LoL，实际是 PowerShell 5.1 的老问题，`Invoke-RestMethod` 把 JSON 数组当成一个对象传给 `Select-Object`，字段全取不到。给命令加括号 `(Invoke-RestMethod ...)` 强制展开即可。教训：测接口先看原始返回，别急着下结论。

**已知限制**
- 不指定战队时只看世界赛，世界赛结束后需要支持选择 LPL、LCK 等联赛。
- 免费套餐没有单局和选手的详细数据。

**邮件提醒**
- 用户可以在“设置”里填写邮箱、开启邮件提醒，并发送测试邮件确认能收到；说明了邮箱只用于发送提醒。
- `NotificationChannel` 接口 + 站内通知、邮件两个实现；`NotificationDispatcher` 自动注入所有渠道，一个渠道失败不影响其他渠道（开闭原则）。
- 提醒邮件用 `@Async` 异步发送，不卡住定时任务；测试邮件同步发送，失败原因直接返回页面。
- 新增数据库迁移脚本 `V2__user_email.sql`，按 Flyway 的命名约定，方便以后接入。

**排查：提醒邮件发送失败**
- 报错是 `MailAuthenticationException: Authentication failed`，但最里层原因是 `SocketTimeoutException: Read timed out`：不是密码错，而是登录时服务器没响应。读异常要看最里层的 `Caused by`。
- 加了“失败重试 3 次 + 退避”，仍然失败，说明不是偶发的网络抖动。
- 测试邮件成功、提醒邮件失败，先怀疑是异步线程的差异；但打开 `mail.debug` 后，测试邮件也失败了，推翻了这个猜测。先看日志再改代码，避免了一次无用的修改。
- 日志显示：连接和加密握手正常，发出登录请求后 163 一直不响应。密码错误会立刻返回 `535`，而不是沉默，所以判断是 163 的反垃圾机制在限制登录。Java 不走 VPN，排除了 VPN 出口 IP 的原因。
- 教训：重试能解决临时故障，但对于“被限流”，立刻重试只会让限流持续更久。更稳妥的做法是“发件箱模式”：失败的邮件写入待发送表，由定时任务隔几分钟、间隔逐渐拉长地重试，重启也不会丢。
- 安全提醒：`mail.debug` 日志里有 Base64 编码的账号和授权码（Base64 不是加密），分享前要打码；调试完要关掉。
- 验证：停止测试 30 分钟、代码不变，15:20 的提醒邮件成功送达手机，证实了限流的判断。整个链路跑通：对话创建提醒 → 定时任务触发 → 分发器 → 站内通知 + 邮件。

**排查：写入的文件被“覆盖回旧版本”**
- 一开始以为是 IDEA 把内存里的旧内容存回了磁盘，但标签页关掉后仍然发生。
- 规律：每次都恢复成“上一次写入的版本”，且第一次写入被恢复、第二次写入就能保留。这更像是写文件的通道本身的问题，而不是 IDEA。
- 对策：每次写入后核对文件大小，被恢复就重写，直到确认生效。教训：先找规律再下结论，别急着把问题归到最先想到的原因上。

**邮件发件箱（Outbox 模式）**
- 新增 `email_outbox` 表：提醒邮件先写入表中，再在后台立即试发一次；失败后由定时任务（每分钟扫描）按指数退避重试，间隔为 1、2、4、8、16、32 分钟，最长 60 分钟，最多 7 次。全部间隔约 63 分钟，能跨过一次 163 限流期。
- 去掉了原来的“立即重试 3 次 + sleep”。测试邮件仍然同步发送，因为用户在页面上等结果。

**设计讨论**
- **存邮箱地址，而不是只存用户 id**：发件箱记录的是“当时决定发给谁”的快照，这张表也能复用到其他邮件；另存 `user_id` 方便排查。
- **先写表再发，而不是失败了才写表**：后者在“发送”和“写表”之间崩溃会丢邮件。写一行约 1 毫秒，远小于一次 SMTP 发送的几秒，瓶颈不在数据库。写表后立即试发，避免等定时任务的延迟。
- **防止重复发送**：“先查再标记”不是原子的，两个线程可能同时读到“待发送”。改为条件更新来抢占（`WHERE status = 'PENDING' AND attempts = 原值`），影响 1 行的那个才去发。和提醒的乐观锁是同一思路，`attempts` 兼做版本号。
- **租约**：在抢占的同一条 UPDATE 里把 `next_attempt_at` 推后 5 分钟。发送途中崩溃时，租约到期后会被自动重新扫到，不需要 SENDING 状态和专门的恢复逻辑。租约要明显长于一次发送的最长耗时（SMTP 超时 10 秒 × 3）。
- **简单熔断**：限流针对的是整个发件账号，一轮里有一封失败就停止本轮，剩下的留到下一轮。
- **标记成功放在 try 外面**：如果出错的是“改状态”这一步，不能当成发送失败去重试，否则会重复发邮件。
- **至少一次投递**：邮件发出后、改状态前崩溃，重启后会再发一封。对提醒来说，收到两封比一封都收不到好。
- 失败原因同时记录最外层和最里层的异常，例如 `MailSendException <- UnknownHostException: smtp.invalid`。

**学到的**
- `@Async` 和 `@Transactional` 都靠代理对象生效，在同一个类里用 `this.xxx()` 调用会绕过代理，注解失效。
- MySQL 的 `DATETIME` 会把小数秒四舍五入，可能存成“下一秒”；写入前先 `withNano(0)`。
- 在纯单元测试里使用 MyBatis-Plus 的 Lambda 条件构造器，要先用 `TableInfoHelper.initTableInfo` 初始化实体的元数据。
- 模拟故障时用 `.invalid` 域名（RFC 2606 保留），连接在 DNS 阶段就失败，不会触碰真实服务器的风控。

**验证**
- 单元测试全部通过。把 SMTP 地址改成 `smtp.invalid` 后，表里的 `attempts` 递增，重试间隔逐次拉长，`last_error` 记录了失败原因；改回地址并重启后，状态变为 `SENT`，手机收到邮件，证实重启不会丢邮件。

**思考题：提醒的抢占和写入发件箱不在同一个事务里**
- 两条 SQL 之间崩溃：提醒已经标记为完成，但邮件没有入箱，既发不出去也无从重试。
- 方向：放进同一个 MySQL 事务（事务性发件箱，Transactional Outbox）；SMTP 发送必须在事务提交之后才触发。Lua 脚本只能保证 Redis 内部的原子性，管不到 MySQL。

## 2026-11-03（周二）：事务性发件箱

**成果**
- 提醒的“抢占 + 写站内通知 + 写入发件箱”放进同一个事务：任何一步失败都整体回滚，提醒保持待提醒，30 秒后重新触发。解决了昨天的思考题：不会再出现“提醒标记完成了，邮件却没进发件箱”。
- 立即试发改为事务提交之后才触发（`@TransactionalEventListener`），回滚时不会发出数据库里不存在的邮件。
- 新增 `ReminderFirer`，负责触发单条提醒；`ReminderService.fireDue` 循环调用它，每条提醒一个独立的事务。

**设计要点**
- **事务里只放能回滚的事**：写提醒表、站内通知表、发件箱表。发邮件、调接口、调大模型这类回滚不了的事，等提交之后再做。邮件发出去就收不回来，所以不能和数据库的修改绑在一起。
- **`@Transactional` 也有自调用问题**：和 `@Async` 一样靠代理生效，`fireDue` 用 `this` 调用同类方法时事务不会开启。两种解法：挪到另一个 Bean（选了这个，类名按职责起作 `ReminderFirer`），或者用 `TransactionTemplate` 编程式地开事务（它是一个类，不是注解，自己调用，不依赖代理）。
- **每条提醒一个事务**，不包住整个循环：否则一条失败，同一轮的提醒全部回滚。
- **`NotificationDispatcher` 不再 catch 渠道异常**：在事务里吞掉异常，事务会照常提交，通知就悄悄丢了。现在每个渠道只写数据库，外部发送的失败由发件箱隔离和重试，“一个渠道失败不影响其他渠道”的职责交给了发件箱。
- **立即试发只是优化，定时任务才是兜底**：就算提交后应用崩了、事件没处理，邮件已经在表里，定时任务一分钟内会扫到。
- 代价：如果某条提醒因为 bug 每次都失败，它会每 30 秒重试、报一次错。可以接受，报错本身就是在提示去修。

**原理**
- `@TransactionalEventListener`：发布事件时如果正处在事务中，Spring 先把监听器登记在这个事务名下，提交成功后才调用，回滚则作废。`fallbackExecution = true` 表示没有事务时直接执行。
- 事务是绑定在**线程**上的（`ThreadLocal`），换了线程就“看不到”原来的事务。这和流式对话时工具线程拿不到 `SecurityContext` 是同一个原因。
- 原子性的工具要和数据所在的系统对应：Redis 内部用 Lua 脚本，MySQL 内部用事务。跨系统（MySQL 和 SMTP、MySQL 和 MQ）没有能同时管住两边的事务，这正是发件箱模式要解决的问题。

**验证**
- 单元测试通过。把 `email_outbox` 表临时改名，让写入发件箱必定失败：提醒保持 PENDING，站内通知也没有写入，控制台每 30 秒报一次错。把表名改回后，不用重启，30 秒内只弹出一次通知并收到邮件，发件箱状态为 `SENT`。只弹一次，证明失败的那几轮站内通知确实跟着回滚了。

**MySQL 放进 Docker**
- `compose.yaml` 新增 MySQL 8.4：第一次启动时自动建库，创建只能访问 `jarvis` 库的 `jarvis` 账号，并执行 `schema.sql` 建表。换电脑时只需复制 `.env`，再执行 `docker compose up -d`。
- 本机原来的 MySQL 保留。用 `mysqldump` 把数据一次性导入容器，账号、会话、提醒都搬过来了。
- README 更新为现在的项目定位，并写上完整的环境搭建步骤。

**设计要点**
- **端口映射是“宿主机:容器”**：本机 MySQL 占着 3306，容器映射到 3307，两个并存，以后开发别的项目也不受影响。
- **只绑定 `127.0.0.1`**：Docker 默认绑定所有网卡，同一个局域网的人也能连上。顺便修正了 Redis：它没有密码，之前却对外开放。
- **持久化分两层**：AOF 把每条写命令追加到日志，Redis 重启时重放（RDB 才是快照），防的是进程重启丢数据；volume 防的是容器删除丢数据。容器删除后数据还在，靠的是 volume。
- **初始化脚本只执行一次**：`docker-entrypoint-initdb.d` 里的脚本只在数据目录为空时执行（`down -v` 删掉 volume 后才会再次执行）。以后新增的迁移脚本不会自动生效，这正是 Flyway 这类工具存在的原因。
- **密码放在 `.env`**：Compose 会自动读取它，它不进 Git，提交的是 `.env.example` 模板，和 `application-local.yml` 是同一个思路。没配置时 `${VAR:?提示}` 会直接报错，不会用空密码启动。
- **最小权限**：应用改用专用的 `jarvis` 账号，不用 root。万一应用的密码泄露，影响范围也只有这一个库。
- 镜像固定版本号 `mysql:8.4`，不用 latest，避免镜像更新后版本悄悄变了。
- 已有数据不写进 `schema.sql`：它会提交到 GitHub，而数据里有密码哈希、邮箱和聊天记录。导出时用 `--no-create-info` 只导数据，表结构以 `schema.sql` 为准，顺便检验它有没有漏掉列。

**学到的**
- PowerShell 5.1 的 `>` 会把文件存成 UTF-16，MySQL 读进去是乱码，所以 `mysqldump` 要用 `--result-file`。PowerShell 也不支持 `<`，导入时先 `docker cp` 进容器，再在容器的 `sh` 里重定向。
- Compose 文件里的 `$$` 是转义：表示在容器里取环境变量，而不是在 Compose 解析时替换。
- 健康检查用 `mysqladmin ping -h 127.0.0.1` 走 TCP：初始化建表期间 MySQL 不开放网络，真正启动完成后才显示 healthy。

**踩过的坑**
- **重建 Redis 时报端口被占用**（`Only one usage of each socket address`）：新容器停在 Created 状态。`netstat` 查不到占用者，说明是 Docker Desktop 还没来得及释放旧容器的端口，再执行一次 `docker compose up -d` 就好了。
- 排查时还排除了“本机另装了一个 Redis”的可能。Windows 允许 `0.0.0.0` 和 `127.0.0.1` 同时绑定同一个端口，如果真有，之前应用连的可能一直是本机的 Redis，而不是 Docker 里的。

**个人知识库（RAG）第 1 步：接入向量库**

**RAG 原理**
- 模型只知道训练时见过的内容，问到不知道的事会编出“听起来像真的”回答（幻觉）。RAG（检索增强生成）是先从资料里找出相关内容放进提示词，让模型“开卷考试”。之前用工具结果纠正“詹姆斯在湖人”，就是同一个思路。
- 不把整份资料塞进提示词：装不下（上下文有上限）、太贵（每一轮都要重发）、效果反而差（上下文越长越容易漏掉中间的细节，即 lost in the middle）、更慢。所以每次只挑最相关的几段。
- 怎么挑：资料切块，用向量模型（Embedding）把每块变成一串数字。意思相关的文字向量相近，“手机怎么才能不那么快没电”和“延长电池续航的方法”一个词都不一样，向量却很近。检索就是找离问题向量最近的几块。
- 向量相近是“经常在讨论同一件事”，是程度而不是精确匹配，所以检索结果里会混入不完全对口的内容，最终交给模型来判断。
- RAG 能减少幻觉，但不能消灭：检索不到或找错时模型照样会编。所以要配合“资料里没有就说不知道”和注明出处。

**设计讨论**
- **切块大小**：太大时一块的向量是多件事的“平均”，和哪个问题都不像；太小时上下文被切断（“比例为 20%”不知道说的是什么）。采用几百字一块、按段落等自然边界切、相邻块重叠。找向量的是数据库的索引，块多不影响速度。RAG 擅长找细节，不擅长全局概括。
- **检索做成工具（Agentic RAG）**，而不是每次提问都自动检索：每次都检索会把无关内容塞进提示词，产生噪音；做成工具后，模型能结合上下文改写检索词（“那违约金呢”改写成“租房合同 违约金”）。代价是模型可能该查不查，靠工具描述和系统提示词约束。
- **用户隔离**：模型不参与（会被提示词注入）；工具从 `ToolContext` 拿到可信的用户 id；过滤条件必须放进检索查询本身，不能“先取前 5 块再在 Java 里过滤”，否则可能过滤完一块不剩。
- **两个数据库**：业务数据留在 MySQL，PostgreSQL 只存向量。代价是上传时两边没有共享的事务，需要靠文档状态（PROCESSING / READY / FAILED）+ 重跑前先删旧块（幂等）来保证可恢复；检索时先从 MySQL 查出 READY 的文档 id，再作为过滤条件交给向量检索（跨库不能 JOIN，在应用里拼）。
- **向量模型选阿里云百炼 `qwen3.7-text-embedding`**（1024 维）：国内直连、OpenAI 兼容接口、开发阶段有免费额度。换模型代价很大：不同模型的向量互不兼容，所有资料都要重新向量化。
- 第一版只支持 `.txt` 和 `.md`，单个文件不超过 1 MB；PDF、Word 后续再加。

**实现**
- Compose 新增 `pgvector/pgvector:pg17`，第一次启动时执行 `db/vector/schema.sql`：安装扩展、建 `vector_store` 表和 HNSW 索引（近似最近邻，用少量精度换速度）。
- `spring.ai.model.chat=deepseek`、`spring.ai.model.embedding=openai`：对话和向量化各用一家，OpenAI 模块的画图、语音等能力全部关闭。
- 多数据源：PostgreSQL 的数据源声明为 `@Bean(defaultCandidate = false)`，MySQL 仍由 Spring Boot 自动配置，MyBatis-Plus 和事务管理器不受影响；只有写了 `@Qualifier("vector")` 的地方才用 PostgreSQL。
- 不用 pgvector 的 starter（它会拿默认数据源，也就是 MySQL），手动用 `PgVectorStore.builder(jdbcTemplate, embeddingModel)` 创建。
- 冒烟测试 `VectorSmokeTest`：配置开关打开时，启动后存三句话再检索一句意思相近的话，验证整条链路；测完删除测试数据。

**学到的**
- Spring Boot 只在没有自定义 `DataSource` 时才自动配置；Spring Boot 4 的 `DataSourceProperties` 换到了 `org.springframework.boot.jdbc.autoconfigure` 包。
- Spring AI 2.0 的 PgVectorStore 默认不再自动建表（不兼容的改动）。
- pgvector 镜像里 `POSTGRES_USER` 是超级用户，本地开发先这样用，部署时要另建只读写向量表的账号。

**验证**
- 冒烟测试通过：用“手机怎么才能不那么快没电”检索，相似度依次为 0.713（延长手机电池续航的几个方法）、0.249（红烧肉的做法）、0.207（湖人比赛结果）。正确结果遥遥领先，无关内容在 0.2 左右，之后定检索门槛时参考。

## 2026-11-04（周三）：知识库第 2 步，资料上传和处理

**成果**
- 新增 `knowledge_document` 表和 5 个接口：上传（`.txt`、`.md`，不超过 1 MB）、列表、删除（进回收站）、恢复、失败后重试。
- 上传接口只做校验和入库，马上返回；切块、向量化在后台进行，页面通过 `status` 查看进度（PROCESSING → READY / FAILED）。
- 回收站：删除后保留 7 天可恢复，到期由定时任务永久删除。
- 用 DEVLOG 本身做测试资料：3 万多字切成 47 块，删除、恢复、重复上传、二进制文件都验证通过。

**设计讨论**
- **删除方式**：逻辑删除进回收站，7 天后物理删除。向量块在删除时直接物理删除，恢复时重新向量化（代价只是几分钱），恢复就复用了上传的处理流程。
- **跨库删除的顺序**：MySQL 是唯一的真相来源。删除时先在 MySQL 标记，再删向量块：删块失败也无害，因为检索只看 READY 的资料，残留块搜不到，到期清理时会再删一次。反过来的话，资料还显示可用，向量块却没了，模型可能编造回答。这就是**最终一致性**：暂时不一致，但不影响正确性，最终会一致。
- **永久删除时顺序反过来**：先删向量块，再删 MySQL 记录。否则删块失败时，就没有任何记录指向这些块，它们成了永远没人清理的孤儿。原则：只要还有数据依赖某条记录，就先别删它。
- **删除时 status 改为 DELETED**（而不是只设置 `deleted_at`）：一开始只设置了 `deleted_at`，测试时发现回收站里的资料还显示 READY，`chunkCount` 也不准。对比两种方案：只靠 `deleted_at` 的话，以后哪个查询漏写了这个条件，回收站里的资料就会被搜出来（隐私问题）；改成 DELETED 后，`status = READY` 本身就排除了删除的资料。`status` 和 `deleted_at` 表达同一件事，约定它们总是在同一条 UPDATE 里一起改，避免互相矛盾。
- **处理流程照搬发件箱**：条件更新抢占、10 分钟租约（处理途中崩了，到期会被定时任务重新扫到）、先删旧块再写（幂等）、失败后隔几分钟重试，最多 3 次后标记 FAILED，用户可以手动重试。
- **处理中途被删除**：标记 READY 时条件要求 `status = PROCESSING`，更新影响 0 行；再查发现已被删除，就把这次写进去的块再删一次。

**实现细节**
- 实体叫 `KnowledgeDocument`，避免和 Spring AI 的 `Document`（向量库里的一块）重名。
- 不用 `@TableLogic`：回收站要能查出已删除的资料，还要知道是什么时候删的。
- 切块自己写（`TextChunker`）：按段落 → 长段落按句子 → 合并到约 500 字 → 每块带上前一块末尾 80 字（重叠）。
- 百炼一次最多接受 20 条，按每批 10 条调用。
- 编码：先严格按 UTF-8 解码，失败再按 GB18030（Windows 上的老文件常是 GBK）；去掉 BOM。
- 二进制文件改成 `.txt` 也能传上来，内容里有 `\0`，而 PostgreSQL 的 `text` 存不了它，上传时就拒绝。
- 防重复上传：`(user_id, content_hash)` 唯一索引；哈希按解码后的文字算，同一份内容不管什么编码都算同一份。重复的资料如果在回收站里，提示用户直接恢复。
- Spring AI 默认的重试最多 10 次，全部试完可能比租约（10 分钟）还长，改成最多 3 次快速重试，长间隔的重试交给我们自己的定时任务。
- 列表等查询不带原文 `content`（可能有 1 MB），真正切块时才查。
- 把“描述异常”（最外层 + 最里层）抽成 `Exceptions.describe`，发件箱和知识库共用。

**学到的**
- **已经执行过的迁移脚本不能再改**：在已执行过的库上改了不会生效，新环境执行改过的版本又会和老库不一致，Flyway 还会因为校验和对不上拒绝启动。变更要写新的脚本（这次加了 V5）；`schema.sql` 描述最新的完整结构，可以直接改。
- **MyBatis-Plus 的 WHERE 条件是懒加载的**：`set` 的参数立刻登记，`eq`、`isNull` 等要等生成 SQL 时才登记。单元测试里 Mapper 是模拟的，不会生成 SQL，所以要先调用一次 `getSqlSegment()`，才能检查 WHERE 里的值。
- **测试失败时，先判断是代码错了还是测试错了**：这次断言打出来的 7 个实际值全是 SET 里的，说明是收集数据的方式有问题，而不是 `restore` 的逻辑有问题。
- 接口测试除了 PowerShell + curl，还可以用 Apifox、Postman（环境变量、后置脚本自动保存 token），或者 IDEA 自带的 HTTP Client（`.http` 文件可以和代码一起提交）。
